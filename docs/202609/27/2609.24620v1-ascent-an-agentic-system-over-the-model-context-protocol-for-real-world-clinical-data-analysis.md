## 摘要
从真实世界临床数据中回答流行病学问题，需要医学编码、模式感知的 SQL，以及对关于人群、分母和时间的隐含选择进行验证。我们提出 Ascent，一种智能体系统，它通过共享的模型上下文协议工具接口，为标准化和原生模式暴露医学编码、问答和队列分析能力。我们引入 EpiTrap，一个用于测试系统能否避免已知药物流行病学错误的数据集，并比较固定流水线与智能体在不同模型和编排器下的表现。在使用能力较强的模型时，智能体在原生和标准化模式上分别比固定流水线平均提高 27 和 20 个百分点。这些提升需要更多工具调用和更长运行时间。真实项目中的经验凸显了该系统在可行性评估、诊断迭代和专家引导分析方面的价值。

## Abstract
Answering epidemiological questions from real-world clinical data requires medical coding, schema-aware SQL, and validation of implicit choices about populations, denominators, and time. We present Ascent, an agentic system that exposes medical coding, question answering, and cohort analysis through a shared Model Context Protocol tool surface for standardized and native schemas. We introduce EpiTrap, a dataset testing whether systems avoid recognized pharmacoepidemiological errors, and compare a fixed pipeline with agents across models and orchestrators. With capable models, agents improve accuracy over the fixed pipeline by an average of 27 and 20 percentage points on native and standardized schemas, respectively. These gains require more tool calls and longer runtimes. Experience from real projects highlights the system's value for feasibility assessment, diagnostic iteration, and expert-guided analysis.

- **背景**：从真实世界临床数据（RWD）回答流行病学问题，远不止"把自然语言翻译成 SQL"。分析师还需定义人群与时间窗、把临床概念映射到编码、适配异构 schema，并验证可执行查询是否真的回答了原问题。

- **现有工作的不足**：
  - 对话式/文本到 SQL 系统降低了实现负担，但多为单轮或固定流程，缺乏对隐含假设的显式暴露与修正能力。

- **整体含义**：论文主张用**智能体（agentic）系统**在报告前主动暴露隐含选择、检查中间结果、并修订分析；并以 MCP 共享工具面将"受治理的数据访问层"与"客户端/模型/编排器"解耦，从而同时支持标准化 OMOP-CDM 与厂商原生 schema。

## 2. 方法论

### 2.1 核心思想
- ASCENT 不把分析能力嵌入单一应用或单一 agent loop，而是通过**共享的 Model Context Protocol（MCP）工具面（31 个工具）**暴露能力，实现三点设计属性：
  - **可移植性**：同一工具面支持自托管聊天前端（如 LibreChat）、编码智能体（Claude Code、Cursor、Copilot）等任意 MCP 客户端。
  - **模型无关性**：编排模型/智能体可替换而无需修改工具。
  - **隔离性**：模型只能通过受治理工具访问数据。
- 架构分层：用户通道 → 安全网关（认证/授权/限流/输入筛查）→ 智能体编排器（plan·call·react·retry）→ MCP 工具面 → 方法服务 → 受治理数据存储。

### 2.2 工具面的五类能力
- **Discovery**：枚举可访问数据库、返回机器可读 schema、列出本体、暴露数据源元数据/行数/样例行。
- **Medical coding**：自由文本→标准化编码（如 ICD-10），对词表做校验，并报告每个编码的实际患者数。
- **Question answering**：先做轻量"可回答性"判断（基于 EPIASK KB 检索语料），再用 CLUES 方法对欠定义问题做**歧义消解**（把关键解释呈现给用户确认/编辑），最后经检索增强的 OMOP text-to-SQL 或原生 schema grounded 生成 SQL。
- **Cohorts**：由自然语言入排标准构建队列，支持持久化/共享、attrition funnel（流失漏斗）与人口学/合并症/用药/检验基线摘要。
- **Literature**：检索科学证据，并将 RWD 结果与已发表文献对比。
- 另有**直接 SQL 执行**用于探查陌生表、核验分母、修复错配过滤条件后重新查询。
- **Skills（可选）**：按需加载经审核的分析工作流、可行性检查、数据库特定约定（编码格式、标识符大小写、日期语义），用于"引导而非替代"编排器推理。

### 2.3 方法服务（4 个后端服务）
- **OMOP 查询构建器**：沿用先前的检索增强方法（两步 RAG text-to-SQL + 自愈）；评测部署中使用 Opus 4.8 生成。
- **原生格式查询构建器（本文新增）**，流程为：
  1. 检索包含表、列、类型、抽样值的 **M-Schema** 表示，以及列值分布、哪些列承载本体编码值的映射；
  2. 模型抽取**人群、时间框架、分析步骤**，生成带编码概念占位符的 SQL；
  3. **医学编码器**解析占位符（按来源做规范化，如去点的 ICD 编码、补零的 NDC）；
  4. 在 Snowflake 执行，并依据执行错误**自动修复**（staged SQL + self-healing）；评测部署中使用 Gemini 3.6 Flash。
- **医学编码器**：临床编码器做稠密检索召回候选概念 → LLM 过滤临床一致性 → 领域扩展（后代概念、药物类别成员、NDC 变体）→ 用患者计数指示哪些编码真实存在于目标数据 → 缓存且可追溯的 code list 可跨分析复用。
- **文献检索**：授权语料 + Google + Perplexity。

### 2.4 部署与持久化
- FastAPI 后端；患者级数据存于 Snowflake，RAG 样例、词表索引、code list 分开存储。
- MCP 传递调用者身份，查询以用户自身的 Snowflake 授权执行并留日志；患者数据已去标识化，访问限于受治理的企业边界内。

## 3. 实验设计

### 3.1 评测数据集：EPI TRAP（本文新提出）
- **设计理念（error-first evaluation）**：每题只针对**一个被刻意植入的推理错误**，配有该陷阱专属的 rubric，描述"天真做法如何产生该错误"以及"正确查询必须满足什么要求"。
- **判定标准**：只要回答的逻辑避开了指定错误即算通过，**与工具调用路径或 SQL 修订次数无关（path-independent）**；未产出可执行查询的运行算失败。该标准同时适用于固定流水线与多步智能体，且不需要数值答案键。
- **错误类型覆盖**：结局确定（outcome ascertainment）、入排与分母、时间定义、发生度量（occurrence measures）、缺失、**单位统一（unit harmonization）**、**患病-发病混淆（prevalence–incidence conflation）**、**分母不合格性（如全子宫切除后不做宫颈癌筛查）**、原病偏倚（protopathic bias）等。
- **两个并行版本**：
  - 原生 schema：Optum® 去标识化 EHR（美国医院与诊所），**156 题**；
  - OMOP-CDM：**153 题**（3 个原生题在 OMOP 中不可行）。
- **多评审评分**：Claude Opus 5 与 GPT-5.6 Luna 独立评分（基于问题、rubric、SQL、推理），原生一致性 82%（κ=0.62），OMOP 一致性 87%（κ=0.75）；分歧由 Claude Opus 4.8 依据双方理由与已执行 SQL 裁决。
- 题目与 rubric 由 LLM 起草 + 作者编辑，候选错误经 LLM 辅助文献检索识别。

### 3.2 对比方法与配置
- **基线**：固定机械流水线（生成 SQL → 解析编码 → 执行 → 复述结果，**无修订**）。
- **智能体框架**：Claude Agent SDK、LangGraph、Strands。
- **模型**：Sonnet 5、DeepSeek-V4-Pro、gpt-oss-120b（Claude Agent SDK 仅限 Anthropic 模型，故只测 Sonnet 5）。
- **提示变体**：minimal plain prompt vs. **reflect prompt**（要求对解释、研究设计、结果进行批判）。
- **消融**："no scaffold"——撤掉专用 text-to-SQL 工具，仅保留其余 ASCENT 工具，让智能体自己写 SQL。
- 所有配置均通过**同一个生产 MCP 服务器**、使用 Promptfoo 评测；准确率变化用**配对问题级 bootstrap** 给出 95% 置信区间。

### 3.3 真实使用研究
- 2026-07-12 至 2026-09-21，36 名用户经 LibreChat、Cursor、Claude Code 等客户端发起 **13,002 次调用**；汇总日志会话与研究者撰写的用例报告。

## 6. 主要结论与发现

- **智能体工具使用在强模型上显著提升准确率**：在 10 组 Sonnet 5 与 DeepSeek 配置上平均，原生 schema 较机械流水线提升 **26.7 个百分点**（95% CI [18.7, 35.0]），OMOP 提升 **20.4 个百分点**（95% CI [13.3, 27.5]）。
- **模型能力是前提**：gpt-oss-120b 基本停留在基线水平（原生 −3.0 [−11.2, 5.3]；OMOP +4.6 [−2.0, 11.3]）。
- **反思（reflection）代价高、收益不稳定**：仅在 Claude Agent SDK 上明显有效（75→83 原生，75→82 OMOP），整体平均使工具调用 +27%、运行时间 +13%。
- **专用 SQL 工具对前沿模型不提升准确率**：撤掉后准确率基本不变，但工具调用增加 1.5–2.1×、运行时间反而下降；其价值在于更少交互步骤与可复用的受治理产物（code list、队列等）。
- **真实使用中的失败模式**：① 对错误问题给出看似合理的答案（人群/词表/索引日期/单位/计数粒度错误，如按账单记录而非去重住院次数计数）；② 临床定义"静默漂移"（自动编码扩展越界，或遗漏源数据实际使用的编码）；③ 稀疏数据无警示地报告（把子集当作队列，未记录≠不存在）；④ 单位、时间与终点敏感性。
- **经验教训**：可行性评估本身就是分析产出；真正危险的错误是"静默的"（通过执行校验、返回看似合理数字），因此**流行病学合理性**而非查询成功才是有效验证闸门；常规描述性问题已高度自动化（引用查询准确率 >95%），但研究级流行病学仍需专家判断。
- **总体定位**：系统把工作量从 SQL 实现与 code list 整理，转移到可行性评估、数据质量审计与诊断迭代，**不替代科学判断**。

## 7. 优点

- **架构解耦**：以 MCP 工具面统一暴露能力，实现可移植、模型无关、受治理隔离，避免了"手写单一 agent loop"的封闭性；同时原生支持 OMOP 与厂商原生 schema，这在 RWD 场景中非常实用。
- **评测范式创新**：EPI TRAP 的 **error-first + path-independent rubric** 设计绕开了"参考 SQL 只承认一条解路径"和"枚举所有合法轨迹不现实"两大难题，且无需数值答案键，可迁移到其他 RWD text-to-SQL/智能体系统。
- **覆盖真实陷阱**：题目锚定已公认的药物流行病学错误（单位统一、患病-发病混淆、分母不合格性、原病偏倚等），比单纯执行匹配更贴近分析失效的真实原因。
- **严谨的评分协议**：双 LLM 独立评审 + 裁决 + 报告 κ 一致性 + 配对 bootstrap 置信区间。
- **双 schema 平行实例化**：同一错误在两个数据模型上各有对应版本，便于比较 schema 表示对推理难度的影响。
- **有真实部署证据**：36 名用户、13,002 次调用的使用日志与用例报告，补充了纯 benchmark 无法反映的工作流与失败模式。
- **开放科学**：公开 ASCENT 代码与 EPI TRAP 数据集。

- **失败模式分析偏向描述性**：列举了"静默错误""定义漂移""稀疏数据无警示"等问题，但未给出自动检测或缓解机制的设计与验证，也未统计各失败模式的分布比例。
- **数据与隐私披露有限**：患者级数据规模、去标识化方法细节、跨机构数据边界等未充分展开，影响对其治理方案可推广性的判断。
- **任务范围**：EPI TRAP 聚焦描述性/可行性层面的推理陷阱，未涉及因果推断、生存分析、纵向建模、外部对照臂构建等研究级任务，因此"研究级流行病学仍需专家判断"这一结论虽有定性支持，但缺乏在这些更高阶任务上的定量证据。

## 9. 总体评价与启示

- **定位判断**：ASCENT 的价值不在于"又一个 text-to-SQL 系统"，而在于把**受治理的数据访问层**与**可替换的推理/编排层**解耦，并用 MCP 工具面把流行病学专业知识（编码、队列、可行性、文献）变成模型可调用的显式能力。这是 RWD 分析工程化的一条务实路径。
- **方法学贡献更突出**：EPI TRAP 的 error-first、path-independent 评测设计，可能是本文最易被后续工作复用的部分——它把"评测什么"从"SQL 是否与参考答案一致"转移到"分析是否避开了已知的流行病学推理陷阱"，更贴近真实失效原因。
- **核心经验**：在 RWD 场景中，危险的不是查询失败，而是查询成功却回答了错误的问题；因此**执行成功不能作为验证闸门，流行病学合理性才是**。这一判断对任何构建临床数据智能体的团队都有直接指导意义。
- **适用边界**：常规描述性统计已高度自动化（引用查询准确率 >95%），而研究级问题仍需人类专家参与可行性评估与诊断迭代；系统的实际作用是**转移而非消除**专家工作量。
- **后续值得推进的方向**：等算力下的基线对照；工具级消融与成本-准确率前沿曲线；引入人类专家评分锚点；扩展到因果推断与纵向分析类任务；以及在多数据源、多 CDM 方言上的泛化验证。
