## 摘要
从真实世界临床数据回答流行病学问题需要医学编码、模式感知的 SQL，以及对关于人群、分母和时间的隐含选择进行验证。我们提出 Ascent，一个智能体系统，它通过共享的模型上下文协议工具接口，为标准化模式和原生模式提供医学编码、问答和队列分析功能。我们提出 EpiTrap，一个用于测试系统是否避免已知药物流行病学错误的数据集，并在不同模型和编排器上比较固定流水线与智能体。在使用能力较强的模型时，智能体在原生模式和标准化模式上分别比固定流水线平均提高 27 和 20 个百分点。这些提升需要更多的工具调用和更长的运行时间。来自真实项目的经验凸显了该系统在可行性评估、诊断迭代和专家指导的分析方面的价值。

## Abstract
Answering epidemiological questions from real-world clinical data requires medical coding, schema-aware SQL, and validation of implicit choices about populations, denominators, and time. We present Ascent, an agentic system that exposes medical coding, question answering, and cohort analysis through a shared Model Context Protocol tool surface for standardized and native schemas. We introduce EpiTrap, a dataset testing whether systems avoid recognized pharmacoepidemiological errors, and compare a fixed pipeline with agents across models and orchestrators. With capable models, agents improve accuracy over the fixed pipeline by an average of 27 and 20 percentage points on native and standardized schemas, respectively. These gains require more tool calls and longer runtimes. Experience from real projects highlights the system's value for feasibility assessment, diagnostic iteration, and expert-guided analysis.

## 1. 核心问题与研究动机

- **背景**：从真实世界临床数据（RWD）回答流行病学问题，远不止"自然语言转 SQL"。分析师还需定义人群与时间窗、将临床概念映射为标准化编码、适配异构数据库模式，并验证可执行查询是否真正回答了预期问题。
- **核心痛点**：流行病学问题常对**人群、分母、时间窗**等关键选择保持隐含，导致一条语法正确、执行成功的 SQL 可能"对一个错误的问题给出貌似合理的答案"。这类错误（如单位未统一、患病与发病混淆、分母纳入不适用人群）不会触发执行报错，属于"静默错误"。
- **现有方案的不足**：
  - 对话式/Text-to-SQL 系统（如 ClinQueryAgent、EHRSQL 系列）多依赖单一手工智能体循环或固定流程，缺乏可移植性；
  - 开源 OHDSI 栈（ATLAS/HADES）为规则驱动的 OMOP 队列定义，自然语言支持有限；
  - 商业 RWD 平台（TriNetX、Aetion、Truveta）封闭且平台绑定；
  - 数仓原生系统（Snowflake Cortex Analyst、Databricks Genie）能生成 SQL，但缺少医学编码与流行病学语义。
- **整体含义**：论文主张用**智能体（agent）**在报告前主动暴露隐含选择、检查中间结果并修正分析；同时提出一种**与客户端/模型/编排器解耦**的工程架构，使受治理的数据访问层可被任意 MCP 客户端复用。

## 2. 方法论

### 2.1 核心思想：MCP 工具面而非定制智能体循环

- Ascent 不把分析能力封装进单一应用或智能体循环，而是通过**共享的 Model Context Protocol（MCP）工具面（31 个工具）**对外暴露能力，实现三重解耦：
  - **可移植性**：同一工具面支持自托管聊天前端（LibreChat）、编码智能体（Claude Code、Cursor）及其他 MCP 客户端；
  - **模型无关性**：编排模型或智能体可替换而不改动工具；
  - **隔离性**：模型只能通过受治理工具访问数据。

### 2.2 架构组成

- **客户端层**：聊天 UI、编码智能体等 → **安全网关**（认证、授权、限流、输入筛查）→ **智能体编排器**（plan·call·react·retry，模型无关，可加载可选 Skills）→ **MCP 工具面** → **方法服务** → **受治理数据存储**。
- **五大工具能力组**：
  1. **发现（Discovery）**：枚举可访问数据库、返回机器可读模式、列出支持本体、暴露数据源元数据/行数/样本行；
  2. **医学编码**：自由文本 → 标准化编码（如 ICD-10），验证编码，报告每个编码的患者计数以显示哪些编码真正被使用；
  3. **问答（QA）**：先做轻量**可答性检查**（基于 EPIASK KB 检索语料），再用 **CLUES 方法**消解欠定义问题（向用户呈现关键解释供确认/编辑），最后用检索增强 Text-to-SQL（OMOP）或模式锚定生成（原生模式）翻译为 SQL；
  4. **队列（Cohorts）**：将自然语言入排标准结构化并生成 SQL，可持久化与共享，提供流失漏斗（attrition funnel）和人口学/合并症/用药/检验基线摘要；
  5. **文献（Literature）**：检索科学证据，将 RWD 答案与已发表文献对比。
- **补充**：直接 SQL 执行允许智能体检查陌生表、验证分母、修复范围错误的过滤条件并重新查询；**Skills** 为可选按需加载的已审核工作流（流行病学问答、队列、可行性、数据库怪癖），起引导而非替代作用。

### 2.3 原生格式查询构建器（本文新增）

- **第一步**：检索 M-Schema 表示（表、列、类型、采样值），同时获取列值分布，并标记哪些列携带本体编码值（供医学编码器使用）；
- **第二步**：模型抽取**人群、时间框架、分析步骤**，生成带编码概念占位符的 SQL；
- **第三步**：医学编码器用源适配归一化（如去点 ICD 编码、补零 NDC）解析占位符；
- **第四步**：在 Snowflake 上执行，遇执行错误自动修复（self-healing）。

### 2.4 医学编码器

- 流程：**稠密检索候选概念**（临床编码器）→ **LLM 过滤临床一致性** → **领域扩展**（添加后代编码、药物类别成员、NDC 变体）→ **患者计数**验证编码是否出现在目标数据中 → 缓存且带溯源信息的编码列表可跨分析复用。

### 2.5 部署与持久化

- FastAPI 后端；患者级数据存于 Snowflake，RAG 范例、词汇索引、编码列表分开存储；
- MCP 传播调用者身份，查询在用户 Snowflake 授权下执行并留痕；患者数据已去标识化，访问限于受治理企业边界内。

## 3. 实验设计

### 3.1 新基准 EPITRAP

- **设计理念——错误优先评估（Error-first evaluation）**：现有临床 Text-to-SQL 数据集主要评估单次 SQL 与参考查询/执行结果，无法刻画"先检查模式、跑诊断、再修正定义"的智能体；参考 SQL 会偏袒某一条解题路径，且枚举全部有效轨迹不现实。
- **构造方式**：每个问题针对**一个刻意设计的错误**，配有"陷阱专属评分标准"，描述朴素做法为何产生该错误、正确查询必须满足什么要求。**只要推理逻辑避开了指定错误即算通过**，无论工具调用或 SQL 修正路径；未产生可执行查询的运行判为失败。该标准路径无关，同时适用于固定流水线与多步智能体，且无需数值答案键。由于每项只测一个指定错误，准确率是端到端正确性的**上界**。
- **错误来源**：LLM 辅助文献检索确定候选错误，问题与评分标准由 LLM 起草、作者编辑。覆盖结局确定、入排与分母、时间定义、发生度量、缺失值、单位统一、前驱偏倚（protopathic bias）等。
- **两个并行版本**：
  - 原生 Optum® 去标识化 EHR（美国医院与诊所）：**156 题**；
  - OMOP-CDM：**153 题**（3 项原生题在 OMOP 中不可行）。
- **多评委评分**：Claude Opus 5 与 GPT-5.6 Luna 独立打分；原生模式一致率 **82%（κ=0.62）**，OMOP 一致率 **87%（κ=0.75）**；分歧由 Claude Opus 4.8 结合双方理由与已执行 SQL 裁决，并引用决定性评分条款。

### 3.2 对比方法

- **基线**：固定机械流水线（fixed mechanical pipeline）——按固定顺序生成 SQL、解析编码、执行查询、口述结果，**不允许修正**；
- **智能体配置**：三种编排框架 × 多个模型
  - 编排器：Claude Agent SDK、LangGraph、Strands；
  - 模型：Sonnet 5、DeepSeek-V4-Pro、gpt-oss-120b（Claude Agent SDK 仅限 Anthropic 模型，故只用 Sonnet 5）；
  - 提示变体：极简 plain prompt vs. **reflect prompt**（要求批判解释、研究设计、结果）；
  - **"no scaffold"消融**：撤去专用 Text-to-SQL 工具，仅保留其余 Ascent 工具，让智能体自己写 SQL。
- 所有配置通过**同一生产 MCP 服务器**、用 Promptfoo 评估；平均准确率变化采用配对问题级 bootstrap 计算 95% 置信区间。
