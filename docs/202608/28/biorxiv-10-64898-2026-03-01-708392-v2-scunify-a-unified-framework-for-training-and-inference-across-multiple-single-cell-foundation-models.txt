Abstract 

Single-cell foundation models (scFMs) differ in software requirements and per-formance across downstream tasks and adaptation strategies, complicating comparison and reuse. We present scUnify, a framework that preserves each back-bone’s required processing while separating model-specific trainers, downstream tasks, and adaptation strategies as reusable components. # 1 Background 1

The accumulation of large single-cell RNA sequencing (scRNA-seq) atlases has enabled 2

the pretraining of transcriptional patterns observed across tissues and studies and 3

their transfer to new data. Since 2023, various single-cell foundation models (scFMs) 4

that learn transferable cell representations from large atlases have continued to 5

emerge[1]. Early scFMs, including scGPT, Geneformer, and scFoundation, were pre-6

trained primarily on large scRNA-seq datasets. Those model proofed the applicability 7

to downstream tasks such as celltype classification, batch correction, perturbation 8

prediction, and drug-response prediction[2–4]. Recently, UCE and Nicheformer cover 9

broader biological context into cell representation by exploiting the additional infor-10 

mation such as protein-sequence priors embedded by a protein language or spatial 11 

transcriptomic expression[5, 6]. 12 

However, as the number and scope of scFMs have expanded rapidly, selecting a 13 

appropriate model for researcher’s data and research objective has become complex. 14 

Moreover, evaluation study of various scFMs across multiple datasets and downstream 15 

tasks showed that different scFMs had superior performance depending on the task, 16 

and that no single scFM demonstrated consistently dominated performance across all 17 

comparisons[7, 8]. It suggests that rating the model suitability is inappropriate from 18 

previously reported ranks and that comparing candidate scFMs under the research 19 

context is important. However, scFMs differ in model-specific preprocessing and input 20

To address this gap, we developed scUnify, a framework that enables researchers 74 

to compare multiple scFMs and adaptation strategies for their downstream tasks 75 

and extend new trainable tasks across diverse scFMs. Its core design preserves the 76 

software environment required by each scFM and encapsulates model-specific prepro-77 

cessing, input construction, and forward procedures within a model-specific trainer, 78 

while treating downstream task learning and adaptation strategies as reusable com-79 

ponents separated from the backbone. This separation allows researchers to retain the 80 

same task-learning logic while changing the scFM backbone and independently apply-81 

ing and comparing probing, Full-FT, and multiple PEFT methods. Moreover, when 82 

adding a new trainable task, researchers need only implement its task-specific learn-83 

ing logic through the common task interface, after which the task can be connected 84 

to multiple scFM backbones and adaptation strategies. Beyond supporting these 85 

model–task–adaptation combinations, scUnify provides a core system for scheduling 86 

and managing the growing number of experiments. When multiple experiments are 87 

submitted together, the core system manages run allocation, queuing, execution, and 88 

result collection according to the available computational resources, while researchers 89 

can monitor overall progress through the runtime dashboard. Each run is executed 90 

using an AnnData object and a single configuration file specifying the combination 91 

and execution conditions, with cell embeddings and task-specific predictions returned 92 

in AnnData format for direct compatibility with the scverse ecosystem widely used in 93 

scRNA-seq analysis[17]. 94 

In addition, scUnify provides several supporting features that reflect practical 95 

workflows for using scFMs in scRNA-seq studies. First, researchers who wish to 96 

explore pretrained cell representations before downstream training or use them with-97 

out additional learning can employ a lightweight inference mode that generates frozen 98 

cell embeddings without parameter updates. Second, because cell representations are 99

## 2.1 Overview of the scUnify framework 127 

Fig. 1 Graphical overview of the scUnify framework. (a) Overall workflow of scUnify. An AnnData object and a configuration file define an scUnify run, which performs inference or training through model-specific processing and returns cell embeddings and task-specific outputs in AnnData. (b) The scUnify core system. Multiple runs are scheduled across available computational resources, with mixed-precision computation and Distributed Data Parallel supported within each run. (c) Adap-tation strategies. Backbone adaptation is configured independently of the downstream task module to support Full-FT and multiple Hugging Face PEFT methods. During installation, a separate software environment is automatically prepared for each 131 

supported model. Once installed, researchers can run a selected scFM by providing a 132 

common AnnData input and a configuration file that specifies the model, execution 133 

mode, and analysis conditions. During execution, scUnify selects the corresponding 134 

model environment, applies model-specific preprocessing and input construction, and 135 

then performs inference or training with optimized computational resources manage-136 

ment. The resulting cell embeddings and task-specific outputs are stored in consistent 137 

AnnData fields for subsequent analysis in existing Scanpy and scverse workflows. This 138 

workflow reduces the need to install and switch model-specific environments manu-139 

ally or repeatedly convert input and output formats when analyzing one dataset with 140 

multiple scFMs. 141 

Comparing multiple models and execution conditions for the same dataset and 142 

analytical objective requires repeated management of individual analyses and compu-143 

tational resources. scUnify defines one analysis execution as an scUnify run comprising 144 

an AnnData object and a configuration file, which specifies the model, execution 145 

mode, downstream task, adaptation strategy, and hyperparameters. When multiple 146 

runs are submitted, the Ray-based core system[20] assigns each run to the appro-147 

priate model environment and available CPUs and GPUs, and manages queueing or 148 

concurrent execution according to user-specified resource requirements and resource 149 

availability (Figure 1b). Within an individual run, Hugging Face Accelerate[21] can 150 

apply mixed-precision computation and multi-GPU execution using Distributed Data 151 

Parallel (DDP). Researchers can therefore manage runs within the same execution 152 

system while reducing the repeated work of separately coordinating environments 153 

and resource allocations even when the number of candidate scFMs and conditions 154 

increases. 155

The training mode of scUnify is organized around three independently configurable 156

processing, input construction, pretrained-backbone loading, and the training forward 159

scFoundation, and Nicheformer[2–6]. Within each trainer, the transformer backbone 161 

is connected to the official Hugging Face PEFT library[22] through model-specific tar-162 

get mappings. It allows researchers to change the backbone training scope through 163 

probing, partial fine-tuning, Full-FT, or supported PEFT methods without modi-164 

fying model specific trainer or the task-learning logic (Figure 1c). Meanwhile, the 165

required for a trainable task, and can connect that task to an existing model-168 

specific trainer. Based on this structure, scUnify provides classification, regression, 169

model–task–adaptation combination. 175

## 2.2 scUnify reproduces evaluated model outputs and 188 

## characterizes model-specific computational behavior 189 

To assess the reliability and practical applicability of the common execution workflow, 190 

we examined several quantitative index: numerical consistency of cell embeddings with 191 

the original implementations, training behavior during continual learning, whether 192 

end-to-end inference runtime increased relative to the original workflows under the 193 

evaluated conditions, and whether model-specific resource trade-offs could be com-194 

pared within the same workflow. We also varied numerical precision, batch size, and 195 

the number of GPUs allocated to a run and analyzed the outputs and resource use 196 

of inference and training. In inference mode, we compared cell embeddings generated 197 

by scUnify and the original implementations. In training mode, we performed contin-198 

ual learning using each model’s pretraining objective and tracked the loss trajectories; 199 

Geneformer and Nicheformer, whose original repositories provided comparable contin-200 

ual learning workflows, were also compared directly with their original workflows. The 201 

mean cell-wise cosine similarity was 0.9926–1.0000 across all model–precision condi-202 

tions (Figure 2a). Across precisions, scUnify losses generally followed similar decreasing 203 

trajectories within each model, and the directly compared training-loss trajectories 204

UCE also exhibited precision-dependent optimization behavior, with nearly overlap-207

## 2.3 scUnify enables systematic comparison of scFM backbones 249 

## and adaptation strategies across downstream tasks 250 

scUnify separates the model-specific trainer, the downstream task module and 251 

the adaptation strategy, allowing different combinations of the scFM backbone-252 

downstream task-adaptation strategy to be executed and compared within an 253 

integrated workflow. To evaluate whether this separation could extend model-native 254 

downstream workflows with additional adaptation strategies without reimplementing 255 

task-specific learning logic, we configured trainable workflows reported across the five 256 

scFMs as built-in downstream tasks(Supplementary Table S2, Figure 3). Although 257 

their prediction targets differed, the original studies of the four scFMs other than UCE 258 

each reported a trainable cell-level classification workflow. We retained their model-259 

native workflows(architectures and objectives) and extended celltype classification to 260 

UCE, allowing all five models to be evaluated in a common downstream context. 261 

Additionally, we included niche-density regression for Nicheformer, batch correction 262 

and perturbation prediction for scGPT, and perturbation prediction for scFoundation. 263 

For each downstream task, the model-specific task architecture was kept fixed while 264 

adaptation strategies were independently applied to the corresponding backbone. 265

# 3 Discussion 378 

In this study, we developed scUnify to connect scFM execution, downstream task 379 

learning, and adaptation across distinct software environments and implementation 380 

procedures within a common workflow. Whereas existing scFM integration frameworks 381 

have primarily focused on providing common execution and benchmarking infras-382 

tructure or extending trainable downstream task interfaces[13–16], scUnify differs by 383 

separating the model-specific trainer, downstream task module, and adaptation strat-384 

egy into independent components and supporting their combinations within a unified 385 

execution system. In this design, the model-specific trainer preserves the preprocess-386 

ing, tokenization, and forward procedure of each scFM, the downstream task module 387 

defines the task-specific architecture and objective function, and the adaptation strat-388 

egy independently controls the training scope of the backbone without changing the 389 

task-learning logic. Existing downstream tasks can therefore be executed across multi-390 

ple model and adaptation conditions, while a new trainable task can be implemented 391

Our results illustrate the practical need for this combinatorial design, as the relative 399

We developed scUnify, a framework that connects scFMs separated by different imple-450

extended within a common analytical workflow. Our evaluation showed that scU-452 

nify retained the reliability of integrated execution while enabling direct comparison 453

Task definition and configuration. scUnify defines an analysis execution as an 470

The resulting cell embeddings and task-specific outputs are stored in the obs , obsm ,476

Inference and training modes. Inference and training use separate execution 479

a downstream task module, trainable parameters are selected according to the chosen 483 

adaptation strategy, and the model is trained using the task objective. After training, 484 

predictions and cell embeddings are extracted from the selected checkpoint and stored 485 

together with fold-specific AnnData objects, training histories, and summary artifacts. 486

each configuration through runtime env and manages resource allocation, queueing, 489

the available resources. Runs using the same model environment and dataset share a 491 

Ray Object Store reference to the AnnData loaded by DataLoaderActor . Each run 492 

is executed using Ray TorchTrainer, within which Hugging Face Accelerate[21] han-493 

dles device placement, mixed-precision computation, and multi-GPU execution using 494
